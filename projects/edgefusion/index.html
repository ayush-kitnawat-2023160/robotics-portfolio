EDGE AI / DISTRIBUTED TRACKING

EdgeFusion multi-camera tracking.

Deploying real-time AI detection across camera-equipped Jetson devices, with a shared tracking server.

01 / THE BIG PICTURE

The problem & our solution.

This project investigated how multiple smart camera nodes could detect objects locally and feed a central multi-camera tracking system.

THE REAL-WORLD PROBLEM

Why was this needed?

As camera networks grow, running object detection on every stream at one PC becomes computationally demanding. A scalable system must balance inference speed, camera count and the information exchanged between edge devices and the tracking server.

THE PROJECT GOAL

What did we set out to build?

Deploy optimized YOLO11n and YOLOv8n detection on NVIDIA Jetson Orin Nano units; benchmark one to four simultaneous streams; design multi-camera sensing units that communicate detections and images to a central DeepSORT tracker.

PRACTICAL VALUE

Why does it matter?

By measuring how inference speed changes with camera count, resolution, and FP16/INT8 precision, I could understand the trade-offs involved in running multiple camera streams on edge hardware. Bandwidth savings, end-to-end latency, and cross-camera identity accuracy still need separate evaluation.

⌖
Project context

Independent Project · 2025 · NVIDIA Jetson Orin Nano, FLIR Firefly USB3 cameras, Spinnaker SDK/PySpin, YOLO11n & YOLOv8n, TensorRT, ZeroMQ, central DeepSORT.

02 / OWNERSHIP

What I worked on.

My contribution to the project, separate from the broader team's work.

01

Benchmarked YOLO11n and YOLOv8n on the Jetson Orin Nano across 1–4 cameras, 640×640 or 1440×1080 input, and FP16 versus INT8 TensorRT precision.

02

Deployed and tested optimized YOLO detection on Jetson edge hardware, including its camera input and frame-processing pipeline.

03

Helped design distributed sensing units with three cameras and one Jetson each, connected to a central tracking PC over a high-speed network.

04

Worked on the edge-to-server data pipeline: detection boxes/classes/confidences, encoded full frames and object crops serialized into JSON, then published using ZeroMQ PUSH.

03 / SYSTEM DESIGN

How it works.

01

Capture

FLIR Firefly USB3 cameras stream to a Jetson. Spinnaker SDK/PySpin manages acquisition, auto-exposure and white balance.

02

Detect

YOLO11n / YOLOv8n TensorRT engines run on the edge, producing boxes, class IDs and confidence values.

03

Package & send

Base64-encode full frames and detection crops, combine them with detection metadata in JSON, and send packets using a ZeroMQ PUSH socket.

04

Track centrally

A central server receives and decodes the sensing-unit outputs, with DeepSORT used for tracking and identity association.

04 / THE ENGINEERING

Challenges & what I did.

What made the project difficult, and the choices I made while working through it.

01 / REAL-TIME PERFORMANCE

How many streams can one Jetson handle?

THE PROBLEM

A single model may run quickly, but camera streams compete for limited device compute and memory as their count grows.

MY APPROACH

I benchmarked both YOLO model variants at two resolutions and two precision settings, recording per-camera FPS for one, two, three and four concurrent streams.

Key finding: Tested 32 combinations of model, input resolution, inference precision, and camera count. The benchmark charts below show how throughput changes as streams are added.

02 / EDGE MODEL DEPLOYMENT

Inference speed depends on precision and input size

THE PROBLEM

The practical throughput changes when the detector uses FP16 versus INT8 or processes higher-resolution images.

MY APPROACH

I deployed TensorRT versions of YOLO11n and YOLOv8n and compared the resulting FPS. For YOLO11n at 640×640 with one camera, INT8 reached 20.39 FPS versus 18.92 FPS in FP16.

Key finding: In this one-camera YOLO11n test, INT8 ran faster than FP16. Actual performance depends on the model, resolution, and number of active cameras.

03 / DISTRIBUTED INTEGRATION

Connecting camera nodes to one tracker

THE PROBLEM

Each Jetson must capture images, run detection, and send records that a central server can understand across multiple camera feeds.

MY APPROACH

I helped architect sensing units and a ZeroMQ PUSH/JSON exchange carrying detection metadata and encoded full frames plus crops. The central system was designed around DeepSORT.

Key finding: The system defines how camera nodes send detections and images to the tracking PC. Network usage, end-to-end delay, and cross-camera identity accuracy require further measurement.

“A distributed vision system needs measured throughput and a well-defined data path—not just a fast detector benchmark.”

The FPS measurements reflect detector performance in the tested Jetson configurations, not guaranteed real-world throughput. Bandwidth reduction, end-to-end latency, cross-camera re-identification accuracy, and production reliability have not yet been quantified.
