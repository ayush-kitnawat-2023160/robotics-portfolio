01 / THE BIG PICTURE

The problem & our solution.

A robotic manipulation project that connects what a camera sees to where a real robot arm moves.

THE REAL-WORLD PROBLEM

Why was this needed?

In repetitive sorting and pick-and-place tasks, objects may not always be at fixed positions. A robot cannot act on a camera detection directly because the camera and arm use different coordinate systems.

THE PROJECT GOAL

What did we set out to build?

Use camera calibration and marker-based pose estimation to locate targets, convert their positions into the robot base frame, and send suitable motion commands to an xArm.

PRACTICAL VALUE

Why does it matter?

The approach allows a robot to respond to visually located targets rather than relying only on hard-coded positions. The linked team demonstration shows the physical setup.

⌖
Project context

xArm robotic hardware + camera calibration and ArUco-based observations.

04 / THE ENGINEERING

Challenges & what I did.

What made the project difficult, and the choices I made while working through it.

01 / FRAMES

Pixel coordinates are not robot coordinates

THE PROBLEM

A pose expressed in the camera optical frame cannot be sent directly to a manipulator expecting base-frame coordinates.

MY APPROACH

Calibrated camera geometry and implemented explicit homogeneous transformations from camera frame to robot base.

Evidence / boundary: The central implementation responsibility documented in the resume.

02 / RELIABILITY

Visual estimates jitter, but hardware needs stable targets

THE PROBLEM

Marker visibility, depth uncertainty and calibration error affect how confidently a position can be used.

MY APPROACH

Used pose estimation from known marker geometry and careful transformation checks before using target estimates in robot commands.

Evidence / boundary: Project demonstration shows the physical perception-to-action pipeline.

03 / INTEGRATION

Perception and actuation have different interfaces

THE PROBLEM

Computer vision returns detections and transforms; the arm controller needs feasible target poses and explicit motion commands.

MY APPROACH

Built the connection from estimated target pose to xArm API calls, keeping visual localization and actuation as separate stages.

Evidence / boundary: The demonstration and project code are linked below.
